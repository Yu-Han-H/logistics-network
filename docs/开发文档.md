## 一、项目概述

### 1.1 项目背景

某物流公司要在 30 个城市新建仓储节点之间铺设光纤专线，需要在保证全网连通的前提下让铺设总成本最低；同时为日常配送设计「任意两仓之间最短路径」查询工具，支持毫秒级响应。

### 1.2 项目目标

| 编号 | 目标 |
|---|---|
| G1 | 用**双向循环链表**管理 30 个城市节点，支持增删改查、按距离排序 |
| G2 | 用**邻接表**构建带权无向图，边权为城市间经纬度欧氏距离 |
| G3 | 用 **Prim、Kruskal** 两种算法求最小生成树，输出总权值与所有边 |
| G4 | 用 **Dijkstra** 算法求任意两城市间最短路径，输出完整路径与代价 |
| G5 | 提供系统界面，至少 **2 种角色**（管理员、普通用户），增删城市后动态更新 MST 与最短路径 |

### 1.3 技术栈

| 层 | 技术 | 版本 | 说明 |
|---|---|---|---|
| 后端语言 | Java | JDK 21（LTS）| 核心数据结构与算法全部手写 |
| 后端框架 | Spring Boot | 3.2.x | 提供 REST API |
| 后端构建 | Maven | 3.9+ | 依赖管理与打包 |
| 前端框架 | Vue | 3.x（Composition API） | 界面展示 |
| 前端构建 | Vite | 5.x | 前端构建工具 |
| 路由 | Vue Router | 4.x | 页面路由 |
| 状态管理 | Pinia | 2.x | 用户/角色状态 |
| UI 组件库 | Element Plus | 最新 | 表单、表格、菜单 |
| 图可视化 | AntV G6 | 5.x | 邻接表、MST、路径可视化 |
| 数据存储 | 本地文件 | cities.txt | 城市坐标数据 |
| 版本控制 | Git | - | 代码托管 |

> 红线：**链表、图、MST、Dijkstra 必须手写，禁止引入 JGraphT 等第三方算法库。**

## 四、命名规范

### 4.1 总则

- 名称应**见名知意**，使用完整英文单词，避免拼音与缩写（通用缩写如 `id`、`url`、`config` 除外）。
- 同项目内风格统一，不允许出现 `a1`、`tmp`、`test2` 等无意义命名。

### 4.2 Java 命名规范

| 元素 | 规范 | 示例 |
|---|---|---|
| 包 | 全小写，点分隔，不使用复数 | `com.logistics.algorithm.mst` |
| 类 / 接口 | 大驼峰（UpperCamelCase） | `WeightedGraph`、`CityController` |
| 抽象类 | 以 `Abstract` 或 `Base` 开头 | `BaseGraph` |
| 实现类 | 接口名后加 `Impl` | `CityServiceImpl` |
| 异常类 | 以 `Exception` 结尾 | `CityNotFoundException` |
| 测试类 | 被测类名 + `Test` | `WeightedGraphTest` |
| 方法 | 小驼峰（lowerCamelCase），动词开头 | `addCity()`、`findShortestPath()` |
| 变量 | 小驼峰 | `cityCount`、`edgeList` |
| 布尔值 | `is`/`has`/`should` 开头 | `isEmpty`、`hasNext` |
| 常量 | 全大写 + 下划线 | `MAX_CITY_COUNT`、`INF` |
| 泛型参数 | 单个大写字母 | `T`（类型）、`E`（元素）、`K,V`（键值） |
| 枚举 | 类名大驼峰，枚举值全大写 | `Role.ADMIN` |

**方法命名约定：**

| 操作 | 前缀 | 示例 |
|---|---|---|
| 查询 | `get` / `find` / `list` | `getCity(id)`、`listAll()` |
| 新增 | `add` / `save` | `addCity(city)` |
| 修改 | `update` | `updateCity(city)` |
| 删除 | `delete` / `remove` | `deleteCity(id)` |
| 判断 | `is` / `has` | `contains(city)` |

### 4.3 前端命名规范

| 元素 | 规范 | 示例 |
|---|---|---|
| 组件文件 | 大驼峰（PascalCase） | `NetworkGraph.vue`、`AppMenu.vue` |
| 页面文件 | 大驼峰，以 `View` 结尾 | `CityManageView.vue` |
| 普通 JS 文件 | 小驼峰 | `request.js`、`auth.js` |
| 组件名 | 大驼峰，多词 | `<NetworkGraph />` |
| 变量 / 函数 | 小驼峰 | `cityList`、`fetchMst()` |
| 组合式函数 | `use` 开头 | `useUser()` |
| 常量 | 全大写 + 下划线 | `API_BASE_URL` |
| Props | 小驼峰（声明）/ 短横线（模板） | `:graph-data` |
| CSS 类 | 短横线（kebab-case） | `.city-table`、`.menu-item` |
| 路由 name | 小驼峰 | `cityManage` |
| 路由 path | 短横线 | `/city-manage` |
| Store | `useXxxStore` | `useUserStore` |

### 4.4 数据文件与字段命名

- 数据文件名：全小写 + 短横线或下划线：`cities.txt`。
- 文件内字段：与 Java 模型字段保持一致（小驼峰）。

```
# cities.txt 示例（字段：id name longitude latitude）
1000 北京 116.41 39.90
1001 上海 121.47 31.23
```

### 4.5 REST API 命名规范

- URL 全小写，名词用复数，短横线分隔，**不使用动词**（动词由 HTTP 方法表达）。
- 路径层级不超过 3 层。

| 操作 | 方法 | 路径 |
|---|---|---|
| 查询所有城市 | GET | `/api/cities` |
| 查询单个城市 | GET | `/api/cities/{id}` |
| 新增城市 | POST | `/api/cities` |
| 修改城市 | PUT | `/api/cities/{id}` |
| 删除城市 | DELETE | `/api/cities/{id}` |
| 最小生成树 | GET | `/api/mst?algorithm=prim` |
| 最短路径 | GET | `/api/paths?from={id}&to={id}` |
| 登录 | POST | `/api/auth/login` |

### 4.6 Git 分支与提交规范

**分支命名：**

| 分支 | 用途 | 命名 |
|---|---|---|
| 主分支 | 稳定可交付 | `main` |


示例：`feat: 实现双向循环链表的删除操作`、`fix: 修复Dijkstra路径回溯错误`。

## 五、代码规范

### 5.1 Java 代码规范

- 缩进 **4 个空格**，一般 Tab 默认值。
- 左大括号不换行，右大括号独占一行。
- 方法之间空一行；一个方法尽量不超过 80 行。
- 数据结构类必须包含：无参构造、必要的 getter/setter、`toString()`。
- 手写数据结构需处理边界：空链表、单节点、头节点、越界访问。
- 资源（文件读取）使用 try-with-resources 自动关闭。

### 5.2 前端代码规范

- 缩进 2 个空格。
- 统一使用 **Composition API + `<script setup>`**。
- 优先使用 `const`，需要重新赋值才用 `let`，不使用 `var`。
- 组件按顺序组织：`<template>` → `<script setup>` → `<style scoped>`。
- 样式默认加 `scoped`，避免全局污染。
- 接口请求统一放在 `src/api/`，不在组件内直接写 URL。

### 5.3 注释规范

- 注释描述「为什么」，而非「做什么」（代码本身应表达做什么）。
- **类、核心方法必须写 Javadoc / JSDoc**，说明参数、返回值、异常。
- 复杂算法需在关键步骤处加注释，便于答辩讲解。

```java
/**
 * Dijkstra 单源最短路径。
 * @param source 起点城市 id
 * @return 各城市到起点的最短距离
 */
public Map<Integer, Double> shortestPath(int source) { ... }
```

## 六、接口设计规范

### 6.1 统一响应格式

所有接口返回统一结构：

```json
{
  "code": 200,
  "message": "success",
  "data": { }
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| code | int | 状态码，200 成功 |
| message | string | 提示信息 |
| data | object/array | 业务数据 |

### 6.2 常用状态码

| code | 含义 |
|---|---|
| 200 | 成功 |
| 400 | 请求参数错误 |
| 401 | 未登录 / 登录失效 |
| 403 | 无权限（普通用户访问管理接口） |
| 404 | 资源不存在（城市不存在） |
| 500 | 服务器内部错误 |

### 6.3 核心数据 JSON 示例

**城市对象：**

```json
{
  "id": 1000,
  "name": "北京",
  "longitude": 116.41,
  "latitude": 39.90,
  "nextCity": "上海",
  "prevCity": "西安"
}
```

**最小生成树：**

```json
{
  "algorithm": "prim",
  "totalWeight": 4335.62,
  "edges": [
    { "from": "北京", "to": "沈阳", "weight": 633.90 },
    { "from": "西安", "to": "成都", "weight": 613.80 }
  ],
  "elapsedNanos": 12500
}
```

**最短路径：**

```json
{
  "from": "广州",
  "to": "北京",
  "totalCost": 2123.45,
  "path": ["广州", "武汉", "西安", "北京"],
  "elapsedNanos": 8900
}
```

**图（邻接表，供 G6 渲染）：**

```json
{
  "nodes": [
    { "id": "1000", "name": "北京" }
  ],
  "edges": [
    { "source": "1000", "target": "1001", "weight": 1067.30 }
  ]
}
```

## 七、协作规范

### 7.1 Git 工作流

1. 每人从 `develop` 拉取自己的功能分支：`feature/xxx`。
2. 完成后在本地测试通过，再提交并推送到远程。
3. 通过 Pull Request / Merge Request 合并到 `develop`，至少由 1 人 review。
4. 每个里程碑节点，将稳定的 `develop` 合并到 `main`。
5. **频繁提交、及时拉取**，每天开始前先 `git pull`，减少冲突。

### 7.2 每日同步

- 建议每天用 5-10 分钟同步：昨天完成了什么、今天做什么、遇到什么阻塞。
- 接口字段有变更，第一时间在群里通知并更新文档。

### 7.3 模块边界
